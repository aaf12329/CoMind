## 怎么让另外十一个人用上？

我在想，AI 应该怎么去影响世界？

我还没有什么成熟的好点子。但相比继续讨论最强的模型又进步了多少，我更关心：还有多少人根本没用上这些东西？

借《战争之王》的句式改一下：

> 如果十二个人里，只有一个人已经用上 AI，我的问题是：怎么让另外十一个人也能接触到它？

这里的“十二个人”是表达问题的比喻，不拿来冒充人口统计。真正的问题是，技术已经存在了，为什么一些人仍然够不着？[1]

我想给这个设想起个名字：**Prometheus，普罗米修斯。**

我们应该试着用足够低的价格，让其他人也能接触到这种东西。科技应当平等地流向每一个人。先别把话说得多么宏大，做出一个便宜、能输入问题、能看懂回答的东西再说。

## 先做一个只有文字的终端

目前的想法很直接：用 ESP 做主控，接上输入和显示，发送问题，再把回答显示出来。

先不做语音。麦克风、扬声器以及对应的处理流程暂时都省掉，先把文字问答跑通。

中文确实让人头疼。英文字母的字符集相对小；中文除了显示字形，还得考虑输入法、候选词和选字。**字模库解决的是字怎么画出来，不会顺手把中文输入也解决了。**

我最初想外挂存储芯片放字模库，这是一条路，但不必一开始就认定必须再焊一颗。先看选定模组的 Flash 有多大，程序和字体各占多少，再决定要不要扩展。以 ESP32-C3 为例，不同型号的存储配置需要按具体料号确认。[2]

英文显示也不能只按“26 个字母”算账：大小写、数字和标点都要考虑。普通七段数码管适合显示数字和少量符号，拿来阅读完整 AI 回答不合适，还是得用能显示文字的点阵屏或像素屏。

至于中文字体，可以先估算一下：一个 16×16 像素、每像素 1 bit 的字形，纯位图占 32 字节。假设准备 7000 个这样的字形，就是 224000 字节，约 219 KiB，另加索引等开销。这是按固定条件算的体积，不是实际字库的测量结果；字号、字数和抗锯齿位深都会影响存储量。[3]

## Prompt 和记忆，放到哪里？

问题接着就来了：Prompt 呢？上下文呢？记忆呢？

既然真正的大模型本来就要在服务器上运行，那是不是干脆把 ESP 当作输入输出终端，其他事情交给服务器？

这可以作为第一版的方案：

```text
用户输入
   ↓
ESP 发送消息
   ↓
自己的服务端：管理会话、组装 Prompt、按需读取记忆
   ↓
调用模型 API
   ↓
服务端返回回答 → ESP 分段接收、分页显示
```

设备负责输入、联网、显示和必要的短时缓存；服务端负责模型接入、会话与记忆。设备端先别扛一整套历史记录，也不用每台都维护一份复杂的提示词逻辑。

这样以后修改 Prompt、调整记忆规则，主要改服务端就行。模型供应商的 API 密钥也由服务端保管，设备使用可以单独撤销的访问凭证。

当然，这个划分并没有让成本消失。它只是把一部分成本从设备搬到了服务端：模型调用、存储、网络和长期维护，仍然得有人付钱。

## 便宜，要算到真正用起来

我想压低的是让人用上 AI 的门槛，不能只盯着 ESP 那块板子卖多少钱。

输入设备、屏幕、供电、网络和后续使用费，都得放进账本。第一版可以用 USB 供电，先不加电池；但中文究竟怎么输入，还是必须明确。手机输入可以降低原型难度，如果目标是脱离手机独立使用，就得把实体输入方案补上。

如果一个人本来就有智能手机，也要先想明白：为什么还需要这台设备？它得在价格、操作门槛或者具体使用场景上解决一个实际问题，不能为了做硬件而做硬件。

我的方向暂时就是这样：做一个尽量便宜的文字入口，把复杂的部分交给服务器，再一点一点把使用成本压下来。

Prometheus。先把火送到人手里，别最后做成一件买得起、用不起的摆设。
