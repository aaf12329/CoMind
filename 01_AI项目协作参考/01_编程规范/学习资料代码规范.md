# 学习资料代码规范（通用框架）

版本：1.3 · 整理日期：2026-10-08 · 目录迁移：2026-10-11、2026-10-20（并入 `01_编程规范/`）

> 语言实现细节按 [语言入口](代码规范.md#按语言选择) 读取。

适用范围：各类编程学习资料、算法示例、原理演示、技术对照与小型实验代码。
不限定编程语言、技术领域、运行环境或第三方框架。

目标：一个示例能独立阅读、独立运行，并清楚呈现“输入如何经过处理成为输出”。

本规范只参考 [工程架构规范](工程架构规范.md) 中的模块组织、结构导航与注释方式。
工程项目的跨文件分层、共享模块、统一入口、提交流程等要求不自动继承。
当前任务明确提出的要求优先于本规范。

## 1. 基本原则

1. **一个示例对应一个明确的学习主题。** 不在同一示例中混入多个无关任务。
2. **每个示例文件自行搭起完整体系。** 所需准备、核心逻辑、执行过程、结果展示与入口放在本文件内。
3. **独立示例之间没有代码依赖。** 不导入其他示例或仓库内共享工具才能运行。
4. **通过文件内模块组织保证清晰。** 文件开头必须用注释列出函数结构与树状调用关系。
5. **以学习目标决定实现方式。** 学原理时可以手写，学工具使用时采用现成库，区别要注明。
6. **说明、代码、图片相互对应。** 结果来自哪里、哪些步骤实际执行过，都应可核对。
7. **复杂程度与学习目标匹配。** 不为学习示例额外建立无助于理解的工程框架。

独立运行允许依赖标准库、声明的第三方包、编译工具、外部服务或输入资源；
这里的独立性主要指示例不依赖仓库内部的其他代码文件。

## 2. 分类与目录

**先按学习主题分类，再在主题内区分实现方案或难度。**

已有资料整理时保留合理的课程顺序与分类，新资料根据学习路线安排。
分类名称不固定为模型、算法或框架。

```text
学习资料/
├── 01_主题A/
│   ├── 示例1.<语言扩展名>
│   ├── 示例2.<语言扩展名>
│   ├── figs/                         # 按需提供的配套图片
│   └── README.md
├── 02_主题B/
│   ├── 示例1.<语言扩展名>
│   └── README.md
├── 03_主题C/
├── figs/                             # 可选的全局路线图
├── dependencies/                     # 可选的依赖说明或安装清单
├── 辅助绘图脚本.<语言扩展名>          # 可选，独立于示例执行
└── README.md
```

- 一个主题可以有基础版、进阶版或不同技术实现；不要求每个主题都有同样数量的文件。
- 同一目录中每个示例的学习目标与差异应能从文件名和 README 看出来。
- 多种实现的对照资料优先放在同一主题下，方便并排阅读。
- 不强行创建空目录、占位实现或不适用的技术版本。
- 文件名不要遮蔽语言标准库或第三方包，也不要与编译工具的保留名称冲突。
- 辅助脚本可以单独保留，但不能成为所有学习示例必须调用的公共入口。

## 3. 单文件内部结构

根据任务采用以下通用顺序，不需要的分区可以省略：

```text
文件头说明
依赖声明与可调整参数
① 准备：构造输入、初始化资源或状态
② 核心：算法、业务逻辑或关键对象
③ 执行：组织一次处理、迭代、事件响应或主循环
④ 输出：展示结果、保存产物或可视化
⑤ 入口：按顺序调用以上步骤
```

这里的“模块”指文件内清晰的职责分区，可以由函数、类或语言支持的其他结构实现，
**不意味着必须拆成多个源文件**。

### 文件头

至少说明：

- **学习主题**：这个示例讲什么。
- **任务与输入输出**：接收什么，得到什么。
- **结构导航**：有哪些分区、主要函数或对象，以及各函数的职责。
- **调用关系**：从入口展开的函数调用树，标明父子调用关系。
- **数据流**：输入经过哪些变化到达输出。
- **运行方式**：所需环境和单独运行命令，或对应文档位置。

通用模板：

```text
主题：<本示例的学习内容>
任务：<要完成的具体操作>
结构：① 准备 → ② 核心逻辑 → ③ 执行 → ④ 结果展示 → ⑤ 入口
函数结构：<准备> 负责输入；<执行> 负责处理；<核心逻辑> 负责关键步骤；<展示> 负责输出
调用树：
<入口>
├── <准备>
├── <执行>
│   └── <核心逻辑>
└── <展示>
数据流：<输入> → <中间表示> → <核心处理> → <输出>
依赖：<标准库 / 第三方工具 / 外部资源>
运行：<单独运行命令或操作>
```

以上内容必须写在**代码文件开头的注释或文档字符串中**，位于导入和实现之前，
不能只写在 README 中，也不能只列函数名而省略真实调用关系。

### 函数调用只能是树状

以示例入口为根，本示例自行定义的函数与方法调用关系必须构成一棵树：

- 每个非根函数只有一个直接调用者，不允许多个函数交叉调用同一辅助函数。
- 不允许循环调用、直接递归或间接递归；不能将环展开或重复画节点伪装成树。
- 同一父函数可在循环中多次调用其子函数；这不增加新的父节点。
- 同级步骤之间的数据传递由父函数编排，通过参数与返回值完成，不互相调用。
- 同一父函数下需要复用的操作可以抽取为子函数；不同分支需要相似操作时，
  优先上移到共同父节点调用并传递结果，或保留各分支独立实现，避免形成网状调用。
- 类的方法、构造和本示例提供给框架的回调也应说明，不能通过隐藏调用绕过约束。
  第三方库内部调用不属于本示例函数树；框架接管的调用须另注“由框架调用”，
  不把它误画为入口直接调用。
- 文件头调用树必须与实现一致；新增、删除或移动函数调用时同步更新。

**调用树表达“谁调用谁”，数据流图表达“数据如何变化”，两者不能互相替代。**
树中同级节点按执行顺序排列；分支、循环和框架调度在相应节点旁注明。

### 函数与对象

- 每个函数或对象负责一个可以说清用途的职责。
- 说明输入、返回值与必要约束；数据有结构时标明字段、尺寸、单位或类型。
- 入口只做编排，不塞入全部细节。
- 有持续状态时用明确的对象或状态结构管理，避免大量散落的全局变量。
- 简单任务直接使用简单函数，不为格式统一制造额外抽象。
- 参数尽量集中在文件顶部或明确的参数区，便于修改实验。
- 导入或加载文件时不应意外执行耗时操作或产生写入；具体按语言的入口机制处理。

## 4. 示例独立性与重复

**允许为独立学习保留重复内容。**

- 不同示例可以各自保留输入构造、初始化、输出和基础辅助函数。
- 不为消除这些重复建立仓库内共享层，让读者跨文件才能看完整个流程。
- 同一示例内部出现多次相同操作时，可在满足“只有一个直接调用者”的前提下，抽成本文件内的子函数。
- 一个示例复制到其他位置后，应仍能按说明运行。
- 需要文件、硬件或外部服务时，明确说明获取方式和运行条件。
- 默认提供容易获取、规模适中的演示输入；有条件时使用合成或内嵌数据。

若学习目标本身就是多文件协作、模块系统、工程构建或分布式通信，可以使用多个文件，
但应将该组文件作为一个自包含的学习单元，标出所有组成与运行方式。
这个例外不用于替其他独立示例建立隐式共享依赖。

## 5. 实现方式与技术对照

根据学习目标选择：

| 学习目标 | 实现方式 |
|---|---|
| 理解机制与算法 | 保留关键原理实现，避免封装掉要学习的部分 |
| 学习库或框架使用 | 使用其标准接口，说明调用与数据契约 |
| 比较不同方案 | 各方案独立成例，使用可比较的任务与输入 |
| 观察行为与结果 | 用小型演示呈现变化，说明参数和观察方法 |

- 不统一要求“全部手写”或“全部调用现成库”。
- 示例中哪些逻辑由自己实现、哪些交给第三方工具，应清楚说明。
- 技术对照尽量采用一致的任务、输入、关键条件与评价口径。
- 有默认行为、精度、初始化或运行平台差异时说明差异。
- 不为了目录对称强行增加不适合的实现方案。
- 原理版与工具版并存时明确命名；归档或删除旧版本按当前任务要求处理。

## 6. 注释与表达

- 文件分区使用统一、醒目的注释形式。
- 函数说明用途，关键注释说明原因、约束或容易误解的地方。
- 变量命名服务于理解；采用公式符号或缩写时先解释含义。
- 数据转换标明前后含义，例如类型、维度、编码、坐标系或单位变化。
- 概念解释尽量贴近相应代码，避免读者不断跳转长篇说明。
- 不逐行重复语法本身，也不写代码已经不符合的陈旧注释。
- 区分示意、假设、期望结果与实际验证结果。
- 明确指标的适用范围，不从演示结果推导未经验证的普遍结论。

## 7. 图文配套

**README、教程说明等承担相似功能的文档，必须画出输入数据结构与形状、代码结构，
并让图中的处理步骤与所讲原理对应。** 图的形式按学习内容选择，不机械套用同一张图。

### 必须提供的结构图

1. **输入数据结构与形状图**：画出输入由哪些字段或轴组成，单条记录如何组织，
   整体数据与批次的形状是什么；存在标签、目标或关联字段时画出配对关系。
   标注数据类型、各轴含义及关键变换后的形状，不能只在正文写一个尺寸。
   对文本、树、图、事件等非规则输入，用节点、字段格、层级或序列示意表达结构，
   并注明长度、规模或可变部分，不强行套成固定张量。
2. **代码结构与调用树图**：画出入口、职责分区、实际函数或方法及其调用关系，
   函数名与实现保持一致；调用关系必须满足第 3 节的树状约束。
   只画目录树、抽象模块名或模型层结构，不能代替函数调用树。
3. **原理与实现对应图**：将原理中的关键步骤对应到具体函数、方法或库接口，
   标明输入、中间表示和输出如何变化。可以与前两图合并，但对应关系必须可辨认。
   数学上的数据流可以分支或汇合；这不代表允许函数调用图变成网状。

例如，原理中的“编码 → 核心处理 → 解码”应分别标出实际承担这些步骤的函数，
而不是只有原理框图却看不出代码位置。使用现成库时标明由哪个接口实现该原理步骤。
没有外部输入的示例，画出内部构造的初始数据或状态，并明确注明“无外部输入”。

Markdown 中的 Mermaid、ASCII 图或嵌入的 PNG / SVG 均可；
图必须能直接阅读，不能只有图片路径、生成脚本或一句“参见代码”。
多份文档可以引用同一份对应图，无需为每份文档重复生成相同图片。

| 要解释的内容 | 合适的图 |
|---|---|
| 组成与职责 | 结构图、模块图 |
| 输入如何变化 | 数据流图、处理流程图 |
| 时间先后、交互或状态变化 | 时序图、状态图 |
| 层级、关系或组织 | 树状图、关系图 |
| 数据分布与实验变化 | 散点图、曲线图、统计图 |
| 操作或界面 | 示意图、界面截图 |

- 结构图标出重要组成、关系与方向；数据图标清变量、单位与来源。
- 多种实现存在重要差异时分别绘图，必要时补充对照图。
- 图片放在对应主题目录内，整体路线图可以放在根目录。
- PNG 适合直接查看；SVG 等矢量格式适合缩放，按用途选择。
- 能重新生成的图保留生成方法或独立脚本。
- 检查文字、箭头、图例、字体与代码是否一致。

**结构示意可以根据代码直接绘制；实验数据必须来自实际运行。**
不能用虚构曲线、占位数值或示意截图冒充实测结果。
图片检查与代码运行验证分别记录。

## 8. 说明文档与运行条件

主题说明至少包含学习目标、示例文件含义、独立运行方式和结果如何解读，
并提供第 7 节要求的输入数据结构与形状图、代码调用树及原理对应关系。
根说明列出分类、学习顺序、已实现内容与所需运行条件。

环境说明按语言与技术实际需求提供：

- 语言或运行时版本、依赖、必要的编译工具。
- 输入资源、设备或服务条件。
- 安装、构建、执行与查看结果的步骤。
- 可复现需要的参数、版本或随机性设置。
- 输出的位置与文件含义。

不固定要求使用某种环境管理器。机器专用路径放在环境说明中，不把个人机器路径写成
所有示例默认可用的运行条件。需要文件路径时，说明路径基准，避免依赖不明确的工作目录。

只有说明而没有对应实现的内容，应标为“尚未实现”，不能写成已完成的示例。

## 9. 整理与验证

推荐过程：

1. 明确主题、学习目的、已有分类与示例范围。
2. 将每个示例组织为完整、清楚的学习单元。
3. 在文件内划分职责，说明调用关系与数据流。
4. 同步运行说明、图片与依赖信息。
5. 按任务要求进行必要验证，并记录实际执行范围。

- 用户指定“暂不测试”时，不运行测试，也不以通过测试描述交付。
- 没有特殊限制时，验证范围与改动和风险相匹配，不强制建立完整测试框架。
- 环境安装成功、依赖能加载、示例能运行、结果正确是不同层次，分别说明。
- 不为学习资料自动增加工程流水线、统一调度系统、插件架构或复杂配置层。
- 删除或归档旧资料前确认有可恢复版本，保留尚未归档的修改。
- 提交、推送、发布等操作依据当前授权，不自动作为整理资料的必经步骤。

## 10. 交付核对

- [ ] 分类与学习主题相符，示例目标明确。
- [ ] 每个示例能独立阅读与运行，特殊运行条件已声明。
- [ ] 文件内部有清晰分区，入口只做编排。
- [ ] 文件开头的注释列出函数结构、职责、完整调用树、数据流与运行方式。
- [ ] 本示例函数调用只有树状关系，无多父节点、交叉调用或递归环；框架调度另有说明。
- [ ] 核心逻辑符合本示例的学习目标。
- [ ] 数据契约、重要参数与结果含义清楚。
- [ ] 配套图文与代码一致，实测结果有真实来源。
- [ ] README 等说明文档画出输入数据结构与形状，以及真实代码结构与函数调用树。
- [ ] 原理步骤与实现函数或库接口逐项对应，图中重要数据变换可追踪。
