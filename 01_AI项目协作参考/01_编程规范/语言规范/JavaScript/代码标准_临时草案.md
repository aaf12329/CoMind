# JavaScript 代码标准（临时）

版本：v0.4 · 草案日期：2026-10-10 · 更新日期：2026-10-11

> 2026-10-25 归档：保留 v0.4 个人临时草案身份。仅在当前任务或项目说明明确采用时适用；归档不等于自动启用，不批量改造现有代码。未采用时按 [工程规范](../../工程架构规范.md) 或 [学习资料规范](../../学习资料代码规范.md) 的对应场景执行。

用途：个人 JavaScript 学习、示例与受本规范约束的协作代码。
目标：写法明确、缩进直观、变量可辨认、调用可追踪。
本文件是个人临时约定，不宣称是 JavaScript 社区通用标准。

适用 `.js`、`.mjs`、`.cjs` 及 JSX 中自己编写的逻辑；使用 TypeScript 时，
排版与调用结构要求同样适用，类型说明优先使用语言原生类型声明。
第三方依赖、自动生成文件和构建产物不按此标准批量改写。
自有代码分为工具库与业务调用树两部分；共同遵守写法、类型和计算规则，结构约束见第 4 节。

## 1. 严禁自增简写，强制显式更新

### 1.1 必须执行的规则

- 禁止前置和后置自增：`++n`、`n++`，包括循环、回调与表达式内部。
- 数值变量加一，统一写为 **`n = n + 1;`**，不写 `n += 1;`。
- 按步长增加，写为 `n = n + step;`，不写 `n += step;`。
- 临时配套约定：自减和减量更新也展开，写 `n = n - 1;` / `n = n - step;`，
  不写 `--n`、`n--`、`n -= step;`。
- 状态修改独立成语句，禁止藏在函数参数、条件判断或返回表达式中。
- 这里限制的是变量更新简写；普通计算表达式 `n + 1` 可以正常使用。

正例：

```js
let count = 0;
const step = 2;

count = count + 1;
count = count + step;
count = count - 1;
```

反例：

```js
let count = 0;

count++;
++count;
count += 1;
console.log(count++);
```

循环中的更新同样展开：

```js
for (let index = 0; index < 3; index = index + 1)
{
    console.log(index);
}
```

### 1.2 保持语义，不机械替换

旧代码如果使用了自增表达式的返回值，必须明确保留“先取旧值”还是“先更新再取值”的顺序。

```js
// 对应“取旧值，再加一”。
let oldCount = 3;
const oldResult = oldCount;
oldCount = oldCount + 1;

// 对应“先加一，再取新值”。
let newCount = 3;
newCount = newCount + 1;
const newResult = newCount;
```

数值类型必须清楚：字符串的 `+` 可能发生拼接；BigInt 加一应写 `n = n + 1n;`。
如果更新目标包含函数调用、复杂索引或访问器，先核对求值次数与副作用，不能做纯文本替换。
依据：[MDN：自增运算符的返回值与类型转换](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Increment)。

React 等框架管理的状态通过框架接口更新，不能把显式赋值规则解释为直接修改状态。
例如下面的更新器只根据旧值计算并返回新值：

```js
// setCount 是 useState 返回的状态更新函数。
setCount
(
    function updateCount(previous)
    {
        return previous + 1;
    }
);
```

`updateCount` 由 React 调用；它的返回值交给 React 保存。
依据：[React：useState 更新器](https://react.dev/reference/react/useState)。

## 2. 缩进追求 Python 式层级，成对括号对齐

### 2.1 基本排版

- 每一级缩进固定为 **4 个空格**，不混用 Tab 与空格。
- 同一逻辑层级使用同一前导缩进；嵌套内容多缩进一级。
- 多行代码块使用 Allman 风格：左大括号另起一行，右大括号与其对齐。
- `if`、`else`、循环等控制结构即使只有一条语句，也写完整大括号。
- 本草案约定语句末尾写分号；不依赖省略分号来表达语句边界。

正例：

```js
function describeCount(count)
{
    if (count > 0)
    {
        return '正数';
    }
    else
    {
        return '零或负数';
    }
}
```

反例：

```js
function describeCount(count) {
  if (count > 0) return '正数';
    else return '零或负数';
}
```

### 2.2 圆括号、方括号和对象大括号

短表达式允许成对括号放在同一行。表达式跨多行时，在语法允许的情况下，
将开闭括号放在同级缩进的独立行；内部内容多缩进一级。
这里的“同一缩进”指行首空格数相同，不要求括号在含有其他文字的行中横向列对齐。

```js
const settings =
{
    initialCount: 0,
    step: 1
};

const values =
[
    1,
    2,
    3
];

const result = calculate
(
    settings.initialCount,
    settings.step
);
```

**语义正确优先于括号位置。**不能把 `return` 与它的返回表达式任意拆到两行，
否则自动分号插入可能导致返回 `undefined`；即使手动写分号，也不能修复这个错误断行。
`throw` 同样不能与要抛出的表达式断开。
复杂返回表达式优先保存到命名变量，再写 `return result;`。

```js
function makeSettings()
{
    const settings =
    {
        initialCount: 0,
        step: 1
    };

    return settings;
}
```

JSX 标签遵循嵌套层级：子元素缩进一级，开闭标签的所在行同级对齐。
不要为追求排版改变箭头函数返回对象、条件表达式或其他结构的含义。
依据：[MDN：return 与自动分号插入](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/return)。

### 2.3 严禁使用三元运算符

**自有代码严禁使用条件（三元）运算符 `条件 ? 值一 : 值二`，统一用明确的 `if / else` 分支表达。**
本条是工程内统一的可读性约定，允许增加代码行数；不表示三元运算符本身存在正确性问题。

- 禁令适用于简单、嵌套及跨行三元表达式，包括赋值、返回值、函数参数、模板字符串、
  JSX 内部表达式和 TypeScript 运行时逻辑；不因表达式短小而例外。
- 条件赋值用 `if / else` 分别赋值；条件返回用各分支的 `return` 明确返回结果。
- 函数参数、JSX 等只能放表达式的位置，先在外部通过分支得到命名结果，再使用该结果；
  必要时提取有明确职责的函数，并按第 4 节归入工具库或业务调用树。
- 替换时，条件求值次数保持不变，只执行选中的分支，并保留与周围代码的执行顺序。
  禁止为了提前准备结果而无条件执行两个分支中的函数调用。
- 分支赋值确需使用 `let` 延迟初始化时，写清原因，并保证每条正常继续执行的路径
  都先完成赋值；分支内抛出错误或直接返回的路径单独说明。
- 本条针对条件运算符 `?:`，不将可选链 `?.`、空值合并 `??` 或 TypeScript 可选属性标记
  误判为三元运算符；这些语法仍按各自用途及其他规则检查。

反例：

```js
const score = 80;
const result = score >= 60 ? '合格' : '不合格';
```

正例：

```js
const score = 80;

/** @type {string} 根据成绩确定的结果；两个分支均在读取前完成赋值。 */
let result;

if (score >= 60)
{
    result = '合格';
}
else
{
    result = '不合格';
}

console.log(result);
```

## 3. 禁止未标明的变量

### 3.1 “标明”的含义

本草案先作以下定义：**变量有显式声明，名称能说明含义，关键数据的类型与来源可查。**
不要求给每个明显的局部常量重复写类型注释。

- 必须先声明再使用：用 `const` 或 `let`；函数参数、解构绑定也属于显式声明。
- 默认用 `const`；需要重新赋值时才用 `let`；本草案不使用 `var`。
- 禁止隐式全局变量，禁止借助随意挂载 `window` / `globalThis` 属性绕过声明。
- 声明时尽量给出初值；确需延迟赋值时写清原因，保证读取前完成赋值。
- 一个声明语句只声明一个变量，便于单独解释与修改。
- 名称写明含义，例如 `count`、`step`、`inputData`；数学推导中的简写需先解释。
- 函数参数、返回值、共享状态字段、外部输入等关键数据必须说明类型与含义。
  对局部变量，名称与初始化仍不足以判断时，再补充类型和来源说明。

正例：

```js
/** @type {number} 当前计数，单位：次。 */
let count = 0;

/** @type {number} 每次点击的变化量。 */
const step = 1;

count = count + step;
```

反例：

```js
count = 0; // 没有 const、let 或参数声明。
step = 1;  // 依赖隐式全局变量。
```

### 3.2 类型和边界

- 纯 JavaScript 使用 JSDoc 的 `@param`、`@returns`、`@type` 等说明关键类型。
- TypeScript 使用原生类型声明；注释补充单位、数据来源与约束。
- 纯 JavaScript 的注释本身不会强制运行时类型；需要时配合类型检查或输入校验。
- 对外部输入，先按声明的数据契约校验，再进行数值运算。
- 非模块 JavaScript 文件默认启用 `'use strict';`；ES 模块本身按严格模式执行。
  严格模式是辅助机制，不能代替变量声明和输入校验。

### 3.3 主动规定允许参与运算的类型

**工程必须主动规定每项运算允许的类型，并在输入边界检查或明确转换类型。**
JavaScript 本身允许部分不同类型的值参与运算，并可能发生隐式转换；不能把语言允许执行
理解为业务允许这样计算，也不能仅凭类型注释认为输入已经经过验证。

- 数值计算的操作数默认统一为 `number`；需要 BigInt 时，单独规定为 `bigint`，
  不直接混用 `number` 和 `bigint` 进行算术运算。
- 字符串拼接属于文本处理，必须明确标注；不得把数字字符串直接交给 `+` 进行数值计算。
- 表单、接口、文件、数据库、命令行等外部输入进入内部计算前，先核对数据契约。
  契约要说明允许的类型、格式、单位和范围，以及是否允许转换。
- 不允许转换时，类型不符就拒绝；允许转换时，先检查原始类型和格式，再显式转换，
  最后检查转换结果。不要把空字符串、`null`、布尔值等意外转换为业务数值。
- 当业务要求有限数值时，除 `typeof value === 'number'` 外，还必须检查
  `Number.isFinite(value)`，排除 `NaN` 和正负无穷大。
- 计数、索引等需要安全整数的字段，还应检查 `Number.isSafeInteger(value)` 和业务范围。
  BigInt 与 number 相互转换时，必须明确精度和范围要求，不接受静默丢失精度。
- 内部函数按已约定的类型计算；新的外部输入或不可信数据再次进入时，仍须进行边界检查。

以下是语言行为反例；它们语法合法，但不符合“数值计算只接受约定数值类型”的要求：

```js
const numericText = '3';
const wrongTotal = numericText + 1; // 字符串 '31'，并非数值 4。
const implicitTotal = numericText - 1; // 数值 2，但依赖隐式转换。
const booleanTotal = true + 1; // 数值 2，但布尔值并非约定的数值输入。
```

输入边界示例：本函数的契约明确接受有限 `number`，或可由 `Number` 解析的非空字符串；
其他原始类型一律拒绝。是否允许这种字符串格式，应按具体业务决定。
此处是独立的边界函数片段，可登记为工具库中的校验与转换函数；接入工程时必须记录真实调用点。

```js
/**
 * 校验并转换外部输入；归类：工具库；调用点由接入工程明确登记。
 * @param {unknown} rawInput 外部输入，无默认可信类型。
 * @returns {number} 通过检查的有限数值。
 */
function readNumericInput(rawInput)
{
    let numericValue;

    // 两个合法分支均完成赋值；其他分支抛出错误，避免读取未赋值变量。
    if (typeof rawInput === 'number')
    {
        numericValue = rawInput;
    }
    else if (typeof rawInput === 'string')
    {
        const trimmedInput = rawInput.trim();

        if (trimmedInput === '')
        {
            throw new TypeError('数值输入不能为空字符串。');
        }

        numericValue = Number(trimmedInput);
    }
    else
    {
        throw new TypeError('只允许数值或约定格式的数字字符串。');
    }

    if (!Number.isFinite(numericValue))
    {
        throw new RangeError('输入必须能转换为有限数值。');
    }

    return numericValue;
}
```

如果某个接口只允许 `number`，就应拒绝字符串 `'3'`，不能直接套用上述允许转换的契约。

## 4. 代码结构分为工具库与业务调用树

### 4.1 来源与优先级

参考原文的分层、职责划分、入口编排、文件头结构与真实调用关系要求：

- [工程架构规范：§01、§09、§12](../../工程架构规范.md)
- [学习资料代码规范：§3、§7](../../学习资料代码规范.md)

原工程规范将共享逻辑下沉到共用层及重复消除列为强制要求；学习资料规范则要求示例函数
具有单一直接调用者，且不自动继承工程的共用层与重复消除要求。

本草案 v0.4 按所有者最新要求采用 **“工具库可复用，业务控制流保持严格调用树”**：
工具库不受唯一调用者限制；业务部分仍禁止同级互调、跨分支共享业务函数和循环调用。
这项范围划分替代 v0.3 对全部自有函数的唯一调用者约束。使用本草案的目录须在项目说明中
标明适用范围；与引用规范的结构规则冲突时，本节的两部分划分及各自规则优先。
业务分支无法合理抽成工具时，仍允许重复实现，并登记同步维护关系。

### 4.2 业务调用树的强制约束

1. 先确定职责与层级：入口负责编排；子函数承担清楚的准备、处理、输出等职责。
2. **同层级业务函数或功能模块严禁互相调用。**同级步骤通过父函数传参和接收返回值衔接。
   禁止通过导入同级模块、回调转交或事件广播等方式暗中执行同级功能。
3. 每个业务非根函数只有 **一个直接业务调用者**；多个入口分别展开各自的调用树。
   框架调度入口按第 4.4 节单独登记，不伪造业务父节点。
4. 禁止循环调用、直接递归和间接递归；不能把环展开、复制图节点来伪装成树。
5. 同一父函数可以在循环中多次调用同一子函数，这不增加新的父节点。
6. 不允许两个不同分支都调用同一个业务辅助函数；可由共同父函数调用后传递结果，
   或为不同分支分别实现，并注明重复逻辑及同步维护关系。符合第 4.3 节的工具函数允许共享。
   父函数也可以向同一子函数分别传入不同输入；能否上移需核对数据可得性和执行顺序。
7. 不能为了通过检查，将预先同级的业务互调事后改画成父子层级；重新分层必须有真实职责依据。
8. 类的方法、构造、回调、间接调用都按职责归类并纳入说明；不能只画函数声明而漏掉实际调用点。
9. 文件头调用树必须与代码一致，结构变更时同步更新代码注释和说明文档。

正确：

```text
main
├── prepareInput
├── calculateResult
│   └── increaseValue
└── showResult

数据衔接：main 接收 prepareInput 的结果，再传给 calculateResult，最后传给 showResult。
```

错误：

```text
main
├── prepareInput ─────→ calculateResult   同级互调
└── showResult ───────→ calculateResult   第二个调用者
```

### 4.3 工具库的准入、复用与依赖规则

| 部分 | 职责 | 调用关系 |
|---|---|---|
| 业务调用树 | 用例流程、分支决策、业务状态更新、步骤编排 | 非根节点唯一业务父节点，同级不互调 |
| 工具库 | 通用校验、转换、格式化、基础计算及明确登记的底层接口适配 | 可被多个业务分支复用，内部依赖单向且无环 |

1. 工具库允许多个调用者，也允许同一工具被多个工具复用；必须如实记录这些依赖。
2. 优先写成纯函数：输入输出清楚，不修改输入，不依赖或修改隐藏的业务状态。
   通用性按真实职责判断，不以 `format`、`parse` 等名称前缀或所在目录自动认定。
3. 涉及文件、网络、日志、设备等副作用的底层工具，必须登记副作用、资源与错误契约；
   不得在内部编排业务流程、选择业务分支或直接修改业务状态。
4. **工具库禁止反向调用业务函数**，包括导入业务模块、接收并执行业务回调，
   或通过事件广播触发业务步骤。结果与错误返回给调用者，由业务部分决定下一步。
5. 工具内部依赖可以形成有向无环图；仍禁止循环依赖、直接递归和间接递归。
6. 自有工具同样遵守本文件的禁止自增、禁止三元、缩进、类型边界与计算拆分规则。
7. 先登记职责、输入输出、依赖及副作用，再允许跨分支复用。未归类的自有函数默认按业务函数检查。
   将业务函数搬进工具目录或增加包装层，不能绕过业务调用树规则。
8. 工具库中的重复逻辑应合并维护；业务专属逻辑不得为了消除重复而强行归入工具库。

示意结构与真实调用关系分开记录；下面展示同一个工具被两个业务分支复用：

```text
业务调用树（仅业务节点之间的边）
main
├── handleOrder
└── handleInvoice

工具库及调用点（同一 formatTimestamp 节点，不复制成两个节点）
handleOrder   ──→ formatTimestamp
handleInvoice ──→ formatTimestamp
formatTimestamp ──→ 标准库日期接口

依赖方向：业务 → 工具 → 标准库 / 第三方
```

**业务子图必须是树（多个入口时为多棵树）；包含工具复用边的完整调用图可以有共享节点，
不再要求是严格树。**业务树图必须明确标注范围，并配套工具调用关系表或依赖图；
不能通过隐藏工具调用、复制工具节点或仅画目录结构，声称完整调用图仍是树。

### 4.4 框架调度必须如实标注

- 标准库、浏览器 API、第三方库可以被多个位置调用，不强行复制这些库的实现。
  它们的内部调用不纳入自有业务函数树。
- React 组件、事件处理器、Promise 回调等由框架或运行时调用时，明确标注调度来源和绑定位置。
- 自己定义的回调内部调用哪些业务函数，仍按业务调用树说明；调用工具则登记工具依赖。
  不能借“由框架调用”掩盖业务互调。
- 第三方 API 的自有包装函数按实际职责归类：合格的底层工具允许复用；业务包装仍受唯一父节点约束。
- React 的 **组件嵌套树**、**业务函数调用树**和**数据流图**分开画；JSX 的 `<Child />`
  不冒充父函数直接执行 `Child()`。
- 多事件入口构成多棵明示的树时，分别记录入口；不编造一个不存在的普通函数统一调用它们。
- 一处绑定被框架多次执行，不等于有多个调用者；多个绑定位置仍须分别登记，
  不能因为调度框架相同而合并记录。框架反复调度同一个业务回调可以接受；
  同一回调被两个不同业务父函数直接调用仍属违规。
- 自有状态更新器、事件与 Promise 等回调均纳入职责分类。匿名或内联函数用稳定的
  “文件位置＋绑定用途”标识记录，复杂回调优先命名，不因没有函数名而省略调用关系。

### 4.5 文件头必须包含的内容

1. 学习主题或模块用途。
2. 输入、输出与关键类型。
3. 职责分区、函数结构导航，逐项标明工具或业务归属。
4. 真实业务调用树、工具调用关系及工具内部依赖，标明初始化、重复执行与框架调度。
5. 数据流：输入如何变成结果；调用树不能替代数据流图。
6. 依赖与运行方式。

## 5. 计算尽量逐步拆分，运算范围必须明确

### 5.1 优先使用有含义的中间变量

- 尽量不要写一长串算式；按业务含义或推导步骤拆成独立赋值语句。
- 每个中间变量说明一个计算结果，名称应体现意义，必要时注明类型和单位。
- 短小的单次运算可以直接写，例如 `count = count + 1;`，不要求继续拆分。
- 拆分时保留原来的运算顺序、求值次数和副作用；浮点运算不能随意重排，
  也不能把本来只执行一次的函数调用复制到多步计算中。

正例：把商品总价、运费和优惠分别处理；各金额使用相同单位。

```js
const unitPrice = 120; // 单价，单位：元。
const quantity = 3; // 数量，单位：件；已通过安全整数及业务范围检查。
const shippingFee = 20; // 运费，单位：元。
const discountAmount = 15; // 优惠金额，单位：元。

const goodsAmount = unitPrice * quantity;
const amountWithShipping = goodsAmount + shippingFee;
const payableAmount = amountWithShipping - discountAmount;
```

### 5.2 长算式必须用括号界定运算范围

**确需保留长算式时，必须用括号写明每一步组合关系，不依赖读者比较语言自带的运算优先级。**

- 包含多个二元运算步骤的表达式，用括号明确各步的操作数范围和组合顺序。
  不只是给整个长算式套一层括号。
- 即使运算符相同，也明确组合顺序；例如三个值相加写为 `(first + second) + third`，
  或拆成两次赋值，不写裸露的 `first + second + third`。
- 多层括号难以阅读时，继续拆成中间变量；括号不能代替有含义的步骤划分。
- 复杂比较、逻辑组合采用同样原则，明确各子条件与组合关系。
- 括号是明确运算范围的工具；不能为了排版改变业务公式或原有计算语义。

反例：

```js
const unitPrice = 120;
const quantity = 3;
const shippingFee = 20;
const discountAmount = 15;

const payableAmount = unitPrice * quantity + shippingFee - discountAmount;
const superficiallyGrouped = (unitPrice * quantity + shippingFee - discountAmount);
```

允许的长算式写法；优先采用上面的逐步拆分形式：

```js
const unitPrice = 120;
const quantity = 3;
const shippingFee = 20;
const discountAmount = 15;

const payableAmount = ((unitPrice * quantity) + shippingFee) - discountAmount;
```

## 6. 完整写法示例

### 6.1 无共享工具的业务调用树示例

下面是一个可直接保存为 `counter-example.js` 并用 `node counter-example.js` 运行的单文件示例。
初始输入是一个标量 `number: 0`，加一后输出一个标量 `number: 1`。
此例将 5 个自有函数全部登记为业务部分；标准接口另行标注。

```js
/**
 * 主题：显式加一与严格树状调用。
 * 输入：prepareInput 构造 number 0；输出：控制台打印 number 1。
 * 结构：① 准备 ② 核心计算 ③ 展示 ④ 入口编排。
 * 调用树：
 * main
 * ├── prepareInput
 * ├── calculateResult
 * │   └── increaseValue
 * └── showResult
 * 标准接口：showResult → console.log，第三方内部不展开。
 * 数据流：number 0 → increaseValue → number 1 → console.log。
 * 依赖：JavaScript 运行时，无第三方包。
 * 运行：node counter-example.js
 */
'use strict';

// ① 准备
/**
 * 构造初始计数；唯一调用者：main。
 * @returns {number} 初始计数。
 */
function prepareInput()
{
    return 0;
}

// ② 核心计算
/**
 * 显式增加一次；唯一调用者：calculateResult。
 * @param {number} count 当前计数。
 * @returns {number} 增加一次后的计数。
 */
function increaseValue(count)
{
    let nextCount = count;
    nextCount = nextCount + 1;
    return nextCount;
}

/**
 * 编排本分支的计算；唯一调用者：main。
 * @param {number} input 初始计数。
 * @returns {number} 计算结果。
 */
function calculateResult(input)
{
    const result = increaseValue(input);
    return result;
}

// ③ 展示
/**
 * 打印结果；唯一调用者：main。
 * @param {number} result 待显示的计数。
 * @returns {void}
 */
function showResult(result)
{
    console.log(result);
}

// ④ 入口只编排
/**
 * 按顺序连接准备、计算与输出；调用者：模块入口。
 * @returns {void}
 */
function main()
{
    const input = prepareInput();
    const result = calculateResult(input);
    showResult(result);
}

main();
```

原理与实现对应：

```text
内部构造输入              显式数值更新                    输出
prepareInput()            calculateResult(input)         showResult(result)
number 0          →       increaseValue(count)      →     console.log(1)
                         nextCount = nextCount + 1
```

### 6.2 工具库与业务调用树协作示例

以下单文件示例分为两部分，可保存为 `labels-example.js`，运行 `node labels-example.js`。
大型工程可对应拆为 `tools/` 与 `business/`；目录位置不能代替职责与调用关系检查。

```js
/**
 * 主题：业务调用树与共享工具库。
 * 输入：内部构造的 { orderName: string, invoiceName: string }。
 * 输出：控制台依次打印“订单：订单 A”和“发票：发票 B”。
 * 职责：① 工具库负责清理文字与拼接标签 ② 业务负责选择输入与业务前缀 ③ 入口编排。
 * 业务调用树：
 * mainLabelDemo
 * ├── prepareLabelInputs
 * ├── makeOrderLabel
 * ├── makeInvoiceLabel
 * └── showLabels
 * 工具调用关系：
 * makeOrderLabel   → formatDisplayLabel
 * makeInvoiceLabel → formatDisplayLabel
 * formatDisplayLabel → normalizeDisplayText → String.prototype.trim
 * 标准接口：showLabels → console.log。
 * 数据流：内部文字 → 对应业务分支 → 工具清理与拼接 → 标签 → 控制台。
 * 工具契约：接收 string，返回 string，不修改输入，无隐藏状态及 I/O 副作用。
 * 依赖：JavaScript 运行时，无第三方包。
 * 运行：node labels-example.js
 */
'use strict';

// ① 工具库：允许多个调用者，禁止反向调用业务。
/**
 * 清理显示文字的首尾空白；归类：工具；调用者：formatDisplayLabel。
 * @param {string} value 已按契约提供的文字。
 * @returns {string} 清理后的文字。
 */
function normalizeDisplayText(value)
{
    const normalizedValue = value.trim();
    return normalizedValue;
}

/**
 * 按传入前缀生成标签，不自行选择业务类型；归类：工具。
 * 调用者：makeOrderLabel、makeInvoiceLabel。
 * @param {string} value 待显示文字。
 * @param {string} prefix 由业务提供的前缀。
 * @returns {string} 拼接后的显示标签。
 */
function formatDisplayLabel(value, prefix)
{
    const normalizedValue = normalizeDisplayText(value);
    const label = prefix + normalizedValue;
    return label;
}

// ② 业务调用树：每个非根业务函数只有一个业务父节点。
/**
 * 构造两个业务分支的内部输入；归类：业务；唯一业务调用者：mainLabelDemo。
 * @returns {{orderName: string, invoiceName: string}} 标签输入，无外部输入。
 */
function prepareLabelInputs()
{
    const inputs =
    {
        orderName: '  订单 A  ',
        invoiceName: '  发票 B  '
    };

    return inputs;
}

/**
 * 选择订单前缀并生成订单标签；归类：业务；唯一业务调用者：mainLabelDemo。
 * @param {string} orderName 订单显示名称。
 * @returns {string} 订单标签。
 */
function makeOrderLabel(orderName)
{
    const label = formatDisplayLabel(orderName, '订单：');
    return label;
}

/**
 * 选择发票前缀并生成发票标签；归类：业务；唯一业务调用者：mainLabelDemo。
 * @param {string} invoiceName 发票显示名称。
 * @returns {string} 发票标签。
 */
function makeInvoiceLabel(invoiceName)
{
    const label = formatDisplayLabel(invoiceName, '发票：');
    return label;
}

/**
 * 展示两个标签；归类：业务；唯一业务调用者：mainLabelDemo。
 * @param {string} orderLabel 订单标签。
 * @param {string} invoiceLabel 发票标签。
 * @returns {void}
 */
function showLabels(orderLabel, invoiceLabel)
{
    console.log(orderLabel);
    console.log(invoiceLabel);
}

// ③ 入口只编排。
/**
 * 顺序连接输入、两个业务分支与输出；归类：业务入口；调用者：模块入口。
 * @returns {void}
 */
function mainLabelDemo()
{
    const inputs = prepareLabelInputs();
    const orderLabel = makeOrderLabel(inputs.orderName);
    const invoiceLabel = makeInvoiceLabel(inputs.invoiceName);
    showLabels(orderLabel, invoiceLabel);
}

mainLabelDemo();
```

此例的工具函数只有一份实现；两个业务分支只共享工具，不互相调用。
`formatDisplayLabel` 的两个调用者必须在工具关系中同时出现，不能在完整图中隐藏这次汇合。

## 7. 交付前检查清单

- [ ] 没有前置/后置自增或自减，增减更新已展开为显式赋值。
- [ ] 未把赋值、副作用隐藏在参数、条件或返回表达式中。
- [ ] 自增改写保留了旧值/新值顺序，并确认运算类型。
- [ ] 四空格缩进；多行括号同级对齐；未混用 Tab。
- [ ] `return`、`throw` 等语句的断行保持原语义。
- [ ] 自有代码没有三元运算符；条件选择用明确分支表达，包括 JSX 中的条件选择。
- [ ] 分支改写只执行选中的分支，保留求值次数与顺序；结果变量读取前必定已赋值。
- [ ] 变量先声明再使用；关键参数、返回值、状态字段有说明。
- [ ] 运算允许的类型、单位和范围有明确契约；没有依赖隐式转换的数值计算。
- [ ] 外部输入已在边界检查；允许转换时显式转换并检查结果。
- [ ] 有限数值、安全整数等要求已按业务检查，非法输入有明确处理方式。
- [ ] 长计算已尽量拆成有含义的中间变量；保留长算式时括号明确每一步范围。
- [ ] 未仅给长算式套最外层括号；拆分或加括号未改变求值顺序和副作用。
- [ ] 自有函数已归类；同级业务功能无互调；非根业务函数只有一个直接业务调用者。
- [ ] 没有递归或循环调用；多个业务分支不共享业务辅助函数。
- [ ] 共享工具符合准入要求，不反向调用业务；副作用已明确登记。
- [ ] 工具调用点与内部依赖完整记录，完整图中的共享节点没有被隐藏或重复绘制。
- [ ] 文件头结构导航、业务调用树、工具关系和数据流与实现一致。
- [ ] 框架调度、标准接口、组件结构已分别标注。
- [ ] 验证范围与结果如实记录；反例不标为合规示例。
