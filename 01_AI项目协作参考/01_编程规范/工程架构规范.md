# 工程架构规范（语言无关部分）

> 2026-10-11 从原《代码规范》第二部分拆出，保留原章节编号与工程规则。

> Python 实现细节移至语言规范；原 §10 独立为 [LLM / Agent 项目规范](专项规范/LLM_Agent项目规范.md)。

## 01 · 分层与解耦铁律

```
入口层（壳）      控制台入口 / 图形入口 / 循环调度     ← 全项目唯一有权"横向调用"的层
    │
功能层（模块目录） 各业务模块（I/O、适配、算法、检索…）
    │
共用层（common）  路径地址簿 / 设备 / 绘图 / 通用工具   ← 人人读它，它不调用任何人
    │
标准库 / 第三方
```

- 🔴 **功能层模块之间零 import**——需要共享逻辑就**下沉到共用层**；要协作由入口层编排。
  （唯一例外：一个显式的"适配 / 聚合"模块，须在文件头注明它是特批的横向层。）
- 🔴 **所有文件位置一律从路径地址簿拿**（见第 02 节），严禁各文件自己拼路径。
- 🟡 依赖方向单向向下：入口 → 功能 → 共用 → 标准库；**禁止反向 import 与循环依赖**。
- 🟡 判断标准：画出调用图，应是**树**——若出现横向连线，就是该解耦的地方。

## 02 · 路径地址簿（Store 模式）

- 🔴 全项目的文件 / 目录位置集中登记在**一个路径模块**里（纯常量，不做读写）；
- 🔴 **地址簿只被读、不调用任何人**；新增产物（索引、缓存、导出文件）先登记再使用；
- 🟡 好处：改目录结构只改一处；测试可整体把路径重定向到临时目录（见第 08 节）。

## 03 · 重复的判定与消除（重构操作规程）

- 🔴 **判定**：同一段逻辑出现 ≥2 处 = 重复；出现"改一处要同步 N 处" = 已欠债，尽快还清。
- 🔴 **消除顺序**：① 抽到共用层 → ② 逐文件删本地副本 → ③ 改为 `import` →
  ④ 调用点传参（各文件保留自己的参数常量）。
- 🔴 **重构前先备份、重构后基线对比**：测试通过数不得低于重构前；
  再做运行时冒烟（能 import、能调用、不改输入）。
- 🟡 语言相关的 AST 定位、语法检查与重构实现见对应语言规范；原 Python 操作规程见 [Python 规范](语言规范/Python/代码规范.md#批量重构操作)。

## 04 · I/O 单一入口

- 🔴 同类 I/O 只开**一个口子**：文本读写走同一个函数（自带编码回退），
  结构化数据（JSON 等）单独一个口子，**不开第三处**；
- 🟡 好处：编码 / 换行 / 原子写这些问题只解决一次；要加日志或审计只改一个地方。

## 05 · 返回契约（接口稳定）

- 🔴 一个模块对外**只返回约定的形状**（各语言表示方式见对应语言规范），调用方按契约解包；
  字段名一旦发布就不改（要扩展就加新字段，不改旧字段语义）。
- 🟡 契约写进模块文件头的注释或文档字符串；改契约 = 一次明确的提交（含所有调用点同步）。

## 06 · 错误处理哲学

- 🔴 **给"能修正的人"可操作的提示**：面向模型的错误转成带正确示例的文本
  （自动重试 / 自我修正的命脉）；面向人的错误写清"怎么排查"（含下一个动作）。
- 🔴 **只重试暂时性错误**（429 / 超时 / 5xx，指数退避 + 抖动）；
  4xx 与逻辑错误立刻暴露——重试只会掩盖问题。
- 🟡 单轮失败不退出主循环——每一层都兜住自己的异常。

## 07 · 安全三闸门

| 闸门 | 做法 |
|---|---|
| 路径沙箱 | 真实路径解析 + 限定项目根 + 敏感文件黑名单（`.env` / 私钥） |
| 危险操作审批 | 三态：`ask` / `auto` / `never`；无交互环境（后台线程 / 服务）禁止阻塞式输入 |
| 密钥管理 | 🔴 密钥只进 `.env`，严禁硬编码（教训：明文 key 差点随分享泄露） |

## 08 · 自测规范

- 🟡 模块自测入口使用对应语言的机制；原 Python 入口约定见 [Python 规范](语言规范/Python/代码规范.md#模块自测入口)。
- 🔴 自测**不碰真实数据**：路径重定向到临时目录；
- 🔴 涉网络 / 涉付费接口的自测用**假实现替换**（假模型 / 假响应），零花费；
- 🟡 替换后仍不生效时，检查是否有注册表 / 字典**持有旧函数引用**（踩过的坑）；
- 🟡 GUI / 长任务验证不只看"进程活着"，要断言**具体状态**（像素尺寸、行数、字段值）。

## 09 · 注释与命名

- 🔴 代码文件开头必须用注释或文档字符串写**函数结构树**（分区导航）+ 真实调用关系；函数一行说明说清
  "干什么 / 被谁调用"；行内注释只写"代码看不出来的"（约束、坑、为什么这样做）；
- 🟡 重构时**对外名字能不变就不变**（向后兼容）；
- 🟡 给第三方开源代码加注时，头部标注"结构分析注释 · 非原作者所写"。
- 🔴 学习示例的调用关系只能为树状，具体约束见《学习资料代码规范》第 3 节；
  README 等说明文档必须绘制输入数据结构与形状、代码结构与调用树，
  将原理步骤对应到函数或库接口，不能仅列目录树或模型层图代替。

## 12 · 单文件结构（禁止巨型主函数）

> 逐帧管线 / 摄像头 / 传感器这类"主循环脚本"最容**易**烂成一坨：一个几百行的 main()
> 既开设备、又识别、又判断、又画图、又管按键。本节就是防这个的（由一次真实重构蒸馏）。

**🔴 巨型主函数禁令**：`main()` 只做**编排**——建对象、进循环、按顺序调用功能函数。
一个功能块要留在 main 里，必须能在 30 秒内说清它"吃什么、吐什么"；
说不清就拆成函数，函数超过一屏就拆成模块。

**🔴 单文件三段式**（用注释横幅分区，段与段之间是单向依赖）：

```text
① 判定逻辑    纯逻辑类：只吃数值/坐标/时间，不 import 设备、GUI、推理框架
② 设备与画面   打开设备、构建识别器、绘制文字与图形
③ 主流程 main  读帧 → 更新状态 → 画 → 按键（每帧一圈的目录）
```

① 不碰设备是铁律——它因此可以被合成数据离线单测（见 §08）；② 是①和③之间
唯一的硬件翻译层；③ 退化成一张"每帧做什么"的目录，肉眼扫一遍就知道流程。

**🔴 文件头注释必须包含结构**（三样，缺一不可）：

1. **函数结构树 / 分区导航**——文件分几段、每段有哪些函数；
2. **调用关系总览**——谁调用谁、哪些调用每帧执行、哪些只执行一次；
3. **数据流单行链路**——如：帧 → 关键点 → 指标 → 状态机 → 状态快照 → 屏幕。

学习资料的调用总览必须画成真实调用树；函数结构、调用关系不能只放在 README 中。
对应说明文档还须画出输入数据结构与形状、代码结构及原理对应关系，
具体模板与交付清单见 [学习资料代码规范](学习资料代码规范.md)。

**🔴 状态机封装成类**（"这一帧怎么判"取决于"之前发生了什么"的逻辑，禁止散装变量）：

- 状态（计数器、时间戳、布尔档位、阶段名）全部是**实例字段**；
- 对外窄接口只有 `update(now, 输入) → 状态快照` 与 `reset()`；
- reset 逻辑**只写一份**，构造时与"用户按重置键"共用——两处手抄必然漂移；
- **控制状态与显示状态分离**：给屏幕看的文字/颜色不参与任何判断；
- 🟡 **意图与执行两相**：动作函数只写"目标值"，另一个每帧执行的推进器把"当前值"
  沿缓动曲线向目标走——目标中途变了不用管。

**🟡 配套两条**：路径统一登记见 §02 路径地址簿（"统一路径区"）；跨文件同款的
叶子小函数在头部标注"与 X 同款，需同步修改"。

**🟡 快速自检**：把 main() 读一遍，如果需要滚动超过一屏、或者里面出现了
"打开设备""算指标""画框"混在同一层——就还欠一次拆分。
